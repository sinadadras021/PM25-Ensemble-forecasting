================================================================================
 Multi-strategy deep ensembles for 48-hour urban PM2.5 forecasting
 Reference implementation. Plain-text guide for a first-time reader.
================================================================================

This file describes, step by step, what the code in this repository does. It
describes the code as it stands: every stage, file and default named below is
what runs when you execute the pipeline.

Read this file first, then README.md for commands, then docs/PAPER_MAPPING.md to
locate the function behind any equation in the manuscript.


--------------------------------------------------------------------------------
1. WHAT THE CODE DOES, AND THE QUESTION IT ANSWERS
--------------------------------------------------------------------------------

Given hourly air-quality and meteorological observations from one or more urban
monitoring stations, the pipeline forecasts the next 48 hours of PM2.5 (ug/m3)
at each station.

The study is not asking whether ensembles help -- that is well established. It
asks WHICH WAY OF COMBINING deep forecasters actually works for urban PM2.5.
Four base learners are trained per station, and their forecasts are then
combined six different ways. The six span three strategies, each embodying a
different theory of why combination helps:

  Statistical Averaging        SA, PWE
    Claim: the members are individually noisy but jointly unbiased, so a fixed
    linear blend cancels variance.

  Non-Linear Meta-Learning     MLP-Meta, XGB-Meta
    Claim: how much each member errs depends on the atmospheric state, in a way
    no linear blend can express.

  Context-Aware Selection      H-MOS, SMS
    Claim: the members are specialists. Rather than average them, work out which
    one to trust in the present conditions.

SA -- the plain unweighted average -- has no parameters and therefore cannot
overfit. That makes it the control that every other ensemble has to beat in
order to justify its machinery, and the pipeline reports it alongside the rest
for exactly that reason. When no ensemble beats the best single base learner,
the run log says so rather than leaving the reader to notice.

Nothing in the code is specific to one city or one station. Stations are
discovered by scanning a directory for CSV files; adding a file adds a station.


--------------------------------------------------------------------------------
2. WHAT YOU MUST SUPPLY
--------------------------------------------------------------------------------

One CSV per monitoring station, in a directory of your choosing. No data is
distributed with this repository.

Required columns (exact names and units in docs/DATA_SCHEMA.md):

  Date          hourly timestamp
  PM 2.5 ug/m3  the forecast target
  pollutants    O3, CO, NO, NO2, SO2
  meteorology   temperature, dew point, humidity, pressure, visibility, and
                wind -- either speed and direction, or U and V directly

The path is supplied at run time. There are no hard-coded paths and no
interactive prompts anywhere in the code:

  pm25forecast run-all --config configs/default.yaml --raw-dir /path/to/csvs

Precedence is: built-in defaults, then the YAML config, then environment
variables, then command-line flags.


--------------------------------------------------------------------------------
3. THE PIPELINE, STAGE BY STAGE
--------------------------------------------------------------------------------

Each stage writes its output to disk and the next stage reads it back, so the
stages can be run one at a time while iterating.

STAGE 1 -- PREPROCESS            (src/pm25forecast/pipeline/preprocess.py)
--------------------------------------------------------------------------------
The order of operations in this stage is the whole point of it. The record is
SPLIT FIRST, and only then is anything fitted -- so no transform can ever see
data from a block it is not entitled to.

  1.1  Read the CSV, parse timestamps, place the record on a strict hourly grid.

  1.2  Drop columns that carry no independent information: PM10 (strongly
       collinear with PM2.5, which would let the model read most of its own
       answer off a co-measured channel), NOx (= NO + NO2 by construction), and
       "feel" (a deterministic function of temperature, humidity and wind).

  1.3  SPLIT. Development is 2015-2023, cut 70 % training / 30 % validation with
       a 48-HOUR GAP between them. Test is 2024 and is not touched again until
       stage 4.
         Why the 30 % validation block is large: it is not only an early-stopping
         monitor, it is the ENTIRE TRAINING SET for all six ensembles.
         Why the 48-hour gap: with a 48-hour input window and a 48-hour horizon,
         a window anchored at the last training hour occupies 95 further hours.
         Without the gap the final training windows and the first validation
         windows would overlap almost completely.

  1.4  Screen outliers with the interquartile-range rule, k = 1.5. The bounds are
       computed on the TRAINING block only and then applied. Flagged values are
       VOIDED -- set to missing and handed to the imputer -- never clipped to the
       boundary. Clipping would turn a detectable fault into a plausible
       observation, and applied to the target it would truncate exactly the
       pollution episodes the model exists to predict, so the metrics would
       flatter the model precisely on the days that matter.
       Validation and test LABELS are never screened. A ground truth that has
       been altered is no longer a ground truth.

  1.5  Impute the remaining gaps with k-nearest-neighbours (k = 5), fitted on the
       training block and applied to validation and test.

  1.6  Build features: wind components U and V (Eqs. 1-2), the cyclical hour
       encoding Hour_sin and Hour_cos (Eqs. 3-4), and Hour_offset, an integer
       0-47 that lets the meta-learners model the decay of skill with lead time.

  1.7  Build segments. A segment is a run of consecutive hours with no break.
       Two things break a segment and both are checked: a NaN in a needed
       column, and a hole in the timestamp index.

  1.8  Fit a min-max scaler to [0, 1] on the training block only, apply it, and
       verify afterwards that the fitted block is the one claimed.

  Output: 01_cleaned/<station>.parquet, per-station scalers and IQR bounds, and
  04_results/station_quality_report.csv recording who was admitted and why not.

STAGE 2 -- TRAIN BASE LEARNERS   (src/pm25forecast/pipeline/train_base.py)
--------------------------------------------------------------------------------
  2.1  Cut the record into windows: 48 hours of input, 48 hours of forecast.
         - training and validation use stride 1, so every hour of history
           contributes a sample;
         - test uses stride 48, so no two scored windows share a labelled hour.
           That is what makes the reported sample size honest: with a smaller
           test stride the same observation is scored many times and correlated
           repeats are counted as independent.
       A window never crosses a segment boundary, and a window with any missing
       input value is rejected rather than zero-filled.

  2.2  Train four base learners:
         LSTM and GRU        64 -> 32 units, ReLU
         Bi-LSTM and Bi-GRU  2 x 32 units, ReLU
       All four use Adam, learning rate 0.001, batch 32, up to 100 epochs, early
       stopping with patience 10.

  2.3  Each family trains under a different loss, by design (Table 2):
         LSTM and GRU     -> Inverse-Weighted Loss (IWL, Eq. 19, alpha = 10),
                             which weights each observation by its concentration
                             so the model is not dominated by ordinary hours;
         Bi-LSTM, Bi-GRU  -> Exponential Extreme Loss (EEL, Eq. 20, p = 2),
                             which grows faster than squared error on the high
                             tail, buying accuracy on episodes at some cost on
                             ordinary days.
       Both losses normalise by the COUNT of observed labels, not by the sum of
       the weights. Dividing a weighted loss by its own weight sum cancels the
       weighting exactly -- w times l, divided by w, is l -- leaving a plain MSE
       wearing the name of an extreme-value loss. A test pins this.

  2.4  Cache each member's predictions on validation and test, together with the
       forecast context (meteorology, cyclical time, Hour_offset) that the
       meta-learners will read.

  Output: 02_base_models/<station>/*.keras, member_predictions.npz, history.

STAGE 3 -- FIT THE ENSEMBLES     (src/pm25forecast/pipeline/train_ensembles.py)
--------------------------------------------------------------------------------
All six are fitted on the VALIDATION block predictions, never on in-sample
predictions from the training block, and a guard re-derives the provenance of
the arrays being used before any fit begins.

  SA        Unweighted mean of the four members (Eq. 6). No parameters.

  PWE       Weights optimised by SLSQP subject to the weights summing to one and
            each lying in [0, 1] (Eqs. 7-8). The objective is the mean squared
            error and an analytic gradient is supplied, so the optimiser reaches
            a real optimum rather than reporting convergence at its starting
            point.

  MLP-Meta  A small network, 32 -> 16 -> 8, ReLU, Adam, MSE, reading the member
            predictions together with the forecast context (Eq. 9).

  XGB-Meta  Gradient-boosted trees, 100 estimators, depth 6, learning rate 0.1,
            on the same inputs (Eq. 10). Its top features are recorded.

  H-MOS     Twenty-four hour-specific linear correctors, one per hour of the day
            (Eq. 11). This is the classical model-output-statistics idea applied
            at hourly resolution.

  SMS       A random-forest classifier, 100 trees, depth 6, that predicts WHICH
            member will be most accurate under the present conditions, and then
            uses that member's forecast (Eqs. 12-13). Its selection accuracy and
            its gap from a perfect oracle are both recorded, because a selector
            that is right only as often as chance is not doing what it claims.

  Output: 03_ensembles/<station>/ with each fitted object, plus
  ensemble_meta.json carrying the parts worth reading on their own: PWE's
  optimised weights, the SMS accuracy and oracle gain, the 24 H-MOS coefficient
  pairs, and XGB-Meta's top features.

STAGE 4 -- EVALUATE              (src/pm25forecast/pipeline/evaluate.py)
--------------------------------------------------------------------------------
The 2024 test block is read here for the first time and only once.

  4.1  Produce forecasts for the four members and the six ensembles on identical
       test windows and invert the scaling, so every number is in ug/m3.

  4.2  Aggregate to DAILY MEANS and report Day 1 (hours 1-24) and Day 2
       (hours 25-48) separately. Reporting them separately is what makes the
       decay of predictability with lead time visible instead of averaged away.

  4.3  Score with RMSE (Eq. 14), MAE (Eq. 15), Pearson R (Eq. 16), the Index of
       Agreement (Eq. 17) and Unc% (Eq. 18), at three levels: hourly, daily
       Day 1 / Day 2, and aggregated by strategy.
         R and IOA are reported together on purpose. A forecast that tracks
         every rise and fall but sits 20 ug/m3 too high has R near 1 and a poor
         IOA. Seeing both makes the difference between "wrong shape" and "right
         shape, wrong level" immediately legible.

  Output: 04_results/ -- metrics per station, the city mean, a by-strategy table
  (the comparison the study is making), and predictions_<station>.parquet so any
  figure can be redrawn without retraining.

STAGE 5 -- ABLATION              (src/pm25forecast/pipeline/ablation.py)
--------------------------------------------------------------------------------
Removes one member at a time and REFITS every meta-learner without it, so the
reduced ensemble is the best available ensemble lacking that member. The
degradation therefore measures irreplaceable information rather than a broken
input shape. The chronological split is kept throughout.

  Output: 04_results/ablation_all_stations.csv

  LICENSE                MIT.
  CITATION.cff           How to cite the code.

    default.yaml         The published method. Every value is the one stated in

                         published method. Results produced with these should

    PAPER_MAPPING.md     Every equation and table of the manuscript mapped to
                         the function that implements it.
    METHODS.md           The reasoning behind each stage, and the assumptions
                         and limitations, stated explicitly.

                         pipeline to a different archive.

    cli.py               The command-line entry point; one subcommand per stage.
    config.py            The configuration schema. This file IS the reference:
                         the YAML only overrides fields defined here, and an
                         unknown key raises instead of being silently ignored.
    data/loading.py      Station discovery and CSV reading.
    data/quality.py      The IQR screen, as a two-phase estimator whose fit
                         accepts training data only.
    data/imputation.py   KNN imputation with a recorded fitting block.
    data/segments.py     Contiguity: where the record may and may not be sliced.
    features.py          Wind components, cyclical time, Hour_offset, and the
                         ordered feature list.
    scaling.py           Min-max scaling with a recorded fitting block.
    windowing.py         Sliding windows, vectorised and segment-aware.
    models/base.py       The four base architectures.
    models/losses.py     IWL (Eq. 19) and EEL (Eq. 20), and the assignment of
                         each loss to each model family.
    models/ensembles.py  All six ensembles.
    metrics.py           Every metric in the paper, plus the daily aggregation
                         and the Day 1 / Day 2 split.
    baselines.py         Persistence and climatology references (optional).
    validation.py        The runtime integrity checks.
    seeding.py           Seed 42 and the environment fingerprint.
    logging_utils.py     Run logging.
    pipeline/            One module per stage, in the order described above.

  tests/
    test_paper_fidelity.py  Each test names the paper section or equation it
                            protects, so a changed default fails a test that
                            says which published claim it just broke.
    test_windowing.py       The windowing rules the reported sample size
                            depends on.
    test_end_to_end.py      A complete run on synthetic stations.
    conftest.py             Synthetic stations generated from the mechanisms
                            that actually drive urban PM2.5 -- boundary-layer
                            collapse, traffic peaks, wind ventilation, winter
                            inversions -- then deliberately damaged with
                            outages, instrument spikes and duplicated
                            timestamps.

5. REPRODUCIBILITY
--------------------------------------------------------------------------------

  - Seed 42 is set for Python, NumPy and TensorFlow before any model is built
    (src/pm25forecast/seeding.py), and `deterministic: true` enables
    TensorFlow's deterministic kernels. Re-running the same config on the same
    machine gives the same numbers.

  - The fully resolved configuration is written to resolved_config.yaml at the
    start of every run, so what actually ran is recorded rather than inferred.

  - The environment fingerprint (library versions, platform) is stored beside
    the trained models.

  - Results across different machines or different library versions can differ
    in the last digits. That is a property of floating-point reduction order on
    different hardware, not of this code.


--------------------------------------------------------------------------------
6. WHAT THE CODE REFUSES TO DO
--------------------------------------------------------------------------------

These are enforced while the pipeline runs, so they cannot be quietly broken by
a later edit:

  - fit any transform -- scaler, imputer, or IQR bounds -- outside the training
    block; the configuration rejects the attempt;
  - clip an outlier into range instead of voiding it;
  - screen validation or test labels;
  - fit an ensemble on in-sample base predictions;
  - build a window that crosses a data gap or a split boundary;
  - score overlapping test windows -- the configuration is rejected if the test
    stride is smaller than the forecast horizon;
  - accept an unknown configuration key.


--------------------------------------------------------------------------------
7. LIMITATIONS
--------------------------------------------------------------------------------

Stated plainly, and in full in docs/METHODS.md section 7:

  - Meteorology is taken from the observation archive rather than from a weather
    forecast. An operational system would inherit the forecast's own error.

  - The evaluation covers one city and one test year. Transfer to other networks
    and other years is untested here.

  - The KNN imputer's cost grows quadratically with the number of rows carrying
    gaps, so preprocessing a decade of hourly data takes minutes per station on
    a CPU. This is a runtime characteristic, not an error.
